핵심 관측 · 높은 미사용 비율을 GO로 읽지 않는다

12 screening runs의 disk 절약 tokens는 모두 0이다. Disk read 252회 중 load_state 0회였고, 252회 모두 disk prefix가 resident prefix보다 길지 않았다. 먼저 pop한 record를 복원하지 않아 다음 같은 session까지 보존하지 못했다. Append-only disk 재사용 baseline도 실패했으므로 이 backend/fixture는 일반적인 future-reuse screening에 부적합하다.

해석 · 아직 논문 문제를 확정하지 않는다

미사용 100%는 일반적인 KV/chunk 문제의 증거가 아니다. 선택한 fixture의 native pop-on-lookup과 scores serialization이 지배적이다. Full-state 결과는 fixed chunk mismatch의 증거가 아니다. 실제 trace와 recovery 요구를 확인하지 않아 현실적 GO/NO-GO는 보류한다.

예상 밖의 결과와 correctness 범위

부분 복원은 계측 없는 native 실행과 출력·logits가 정확히 같았지만 cold 실행과는 달랐다. 계측 correctness와 backend numerical equivalence를 구분한다. prefill도 2 threads로 명시했고, 실패 cache와 자원 모니터 race 이력을 보존했다.

Full-state 종료 시점의 다음 설계 · 이후 실행 결과는 아래에 추가

같은 trace를 chunk 64/128/256/512에 paired replay한다. LCP의 oracle reuse, chunk boundary loss, 미저장 tail, 마지막 token 재계산을 분리한다. 이 문단은 full-state 종료 시점의 설계 기록이다. 실제 chunk backend와 batching 효과는 아직 측정하지 않았다. 새 policy/controller는 만들지 않았다.

분석 reference · 실제 chunk backend 측정 아님

판단 · 크기 조정은 크게 완화하지만 아직 시스템 해법은 아니다

256→64로 총 추가 계산은 65.04% 줄었지만 C=64에서도 oracle 대비 30.75% 손실이 남았다. 더 작은 chunk나 partial-tail 지원으로 해결 가능한지, metadata/I/O 비용과 batching trade-off는 미측정이다. 원래 native 재사용 0은 모든 C에서 그대로이며 retention 문제를 chunk 효과로 섞지 않았다. 512는 저장할 full chunk가 없어 unused=0을 좋은 효율로 읽으면 안 된다.

LMCache 실제 backend 비교 · source audit 완료 / 실측 대기

사용자가 64/128/256 비교를 요청했다. LMCache 0.5.5의 고정 commit 05a013b29da78cf2321b9b46ec5039dde2fb0bb0을 확인했다. 기존 token replay는 분석 상한이며 실제 prefill 절약이나 디스크 비용 측정으로 재사용하지 않는다.

save_unfull_chunk는 마지막 짧은 chunk 저장을 제어한다. 조회 key는 chunk 전체 token hash이므로 긴 저장 chunk의 임의 prefix를 재사용한다는 뜻이 아니다. 동일 tail과 연장된 tail의 lookup을 smoke로 구분할 예정이다.

LocalDisk batch write는 key마다 개별 쓰기를 제출한다. Batch read는 metadata lookup 및 여러 파일 읽기를 병렬 처리한다. Controller 메시지 batching과 디스크 payload 합치기는 서로 다르다.

공유 GPU 사용 확인이 필요해 설치/추론을 시작하지 않았다. CPU MP 대안의 POSIX shared memory도 ledger 밖 생성 금지와 조정이 필요하다. 순간 GPU utilization=0은 비어 있다는 증거가 아니다. 현재 연구 결론은 미정이다.
