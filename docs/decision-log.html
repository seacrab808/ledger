provisional

D002 · 첫 독립 도구 후보는 공식 FEMU BlackBox

provisional

이유

D020 · 짧은 pilot와 긴 구간의 관측을 구분해 보존

observed-plateau

이유

동일 FEMU 설정과 70% fill에서 25.20 GiB overwrite를 각 3회 실행했다. 마지막 3 windows 평균 WAF=1.000000/1.900780, erase/GiB=1023.493/1946.245. 6회 모두 수렴 기준 통과=True. 유한 관측 구간과 단일 geometry의 FEMU 모델 근거이며 실기기나 서비스 정책 효과는 미검증이다. 첫 report window native delta는 기존 pilot 6회와 모두 일치했다.

대안

기존 59.5%를 steady-state 차이라고 그대로 사용

현재 선택하지 않은 이유

초기 혼합 배치를 정리하는 비용과 이후 rate가 다를 수 있다. 수렴은 유한 길이의 운영상 기준이며 엄밀한 stationarity 증명은 아니다.

D022 · 작은 history control은 3회 조건 두 runs만 실행

completed

이유

seed 42의 각 패턴 한 run씩, 16.8 GiB/4 windows로 제한했다. 기존 1회 history run의 같은 horizon을 재사용했다. 동일 seed의 random preconditioning 세 번 외 설정은 유지했다.

대안

1회 조건도 rerun하거나 seed 3개와 25.2 GiB를 모두 반복

현재 선택하지 않은 이유

작은 control 요청에 맞춰 같은 byte window의 기존 원본을 재사용한다. n=1이라는 범위 제한을 명시한다.

D023 · Near 판정과 통계적 동등성을 구분

low-selected-history-sensitivity

이유

seed 42의 history control 2개 새 runs: 선택한 두 history의 민감도가 낮음. 1회 조건은 보존된 archive에서 같은 horizon으로 비교했다. n=1/패턴의 기술적 비교이며 전체 초기 상태의 무관함이나 equivalence를 입증하지 않는다.

대안

선택한 history 두 개의 작은 차이를 모든 초기 상태에 일반화

현재 선택하지 않은 이유

수렴 gate와 ±1% 기술적 tolerance는 실행 전에 동결했다. 다른 history/seed/FTL로의 일반화는 아직 열려 있다.

D024 · 주소 순서와 coverage를 구분하는 세 패턴 실험은 설계만

designed-not-executed

이유

S/P는 exact round coverage를 맞추고 P/R은 replacement/coverage 묶음을 비교한다. 검증된 offset sequence와 공통 replay 경로가 필요하다.

대안

바로 solution/서비스/LLM 실험 또는 이름만 permutation인 random workload 실행

현재 선택하지 않은 이유

현재는 메커니즘을 좁히는 단계다. generator/trace correctness를 별도 gate로 설계하고 main 실행은 사용자 승인 후다.

새로운 질문을 발견하면

  • 같은 LBA 순서에서 요청 크기만 바꿔도 GC 호출 시점 때문에 내부 비용이 달라질까?
  • logical fill과 raw NAND의 live occupancy 중 어느 값이 rate를 더 잘 설명할까?
  • 회계로 공정하게 비용을 나누는 것보다 배치로 그 비용 자체를 줄이는 것이 더 강한 해결일까?
  • KV를 덜 저장하면 재계산으로 늘어난 시간 동안 로그·DB가 더 쓰는 비용까지 줄어들까?
  • 주소 갱신을 묶는 host-side scheduling이 같은 bytes에서 GC 복사를 줄일 수 있을까? durability/latency를 지키는 해결 후보이며 아직 미실험이다.
